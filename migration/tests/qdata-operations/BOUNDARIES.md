## Result

No concrete per-pixel Painter BindingStore/qdata resolution defect was found in the inspected current production call graph. The current adapters already enter a scoped slot once per public operation, native dab, scheduled quantum, or dependency check; the numerical loops receive references, copied settings, owned raster objects, or raw bounded arrays. Some repeated resolution is real, but is at those explicit boundaries rather than per pixel. Executable lookup-count coverage accompanies this audit; no pixel-loop lookup defect is claimed.

This is a bounded source audit, not a claim about all arbitrary GObject data keys, every future GEGL operation, every plugin, or all of upstream GIMP. The core implementations and the reachable Painter kernels listed below were inspected, not merely searched for a token. `census.json` provide the whole current textual resolution inventory (29 production source files, 327 matching lines) as a reproducible cross-check, including foundation definitions. Counts in that inventory are source occurrences, not runtime calls.

## Resolution mechanism

`app/painter/binding-store.cpp:43` `find()` is the only Painter-store `g_object_get_qdata()` site. `require()` at line 48 checks the GObject then calls `find()` once and checks the owner thread. `with()` / `read()` in `binding-store.hpp` do not reread qdata; they check admission/thread, retain an owner lease, resolve the typed slot once through `lookup()` -> `entry()` (`binding-store.cpp:65`), then invoke the supplied callback. `entry()` is the actual linear slot search and is the useful second counter. Construction `emplace()` also calls `entry()`, so reset/sample counters after construction when measuring operational cost.

## Repeated resolutions that are not defects

1. Fill/Smudge generic stroke helpers (`painter-native-stroking.hpp:113`) loop over input points and bounded `step()` calls. Lookup totals grow with dabs/steps. They are not expected to be constant for an entire arbitrarily long stroke.
2. Session refresh has up to 16 reconciliation iterations. A slot search at each admission/release stage is not a pixel-loop lookup; coalescing it across signals must preserve current revision/state handling.
3. Filter readiness repeats dependency API calls before and after operations capable of reentry. One pixel chunk can therefore have more than one lookup per dependency. A test should compare equivalent topology/quanta, not assert one lookup for the entire job.
4. Clone `set_source()` resolves once for generation, then `current()` uses `find()` around callback-producing stages (`gimpclonelayer.cpp:297-317`). Undo/edit paths also repeat require() to capture generation. They are finite operation checkpoints and outside projection's pixel loops.
5. Clone double projection currently calls native `gimp_layer_get_opacity(layer)` per pixel (`gimpclonelayer.cpp:436`). This is an optional native scalar-hoisting opportunity, **not qdata/BindingStore resolution and not a newly invented source obligation**.
6. Upstream `app/gegl/gimptilehandlervalidate.c:481`, `gimp-gegl-utils.c:103/:267`, and `gimp-operation-config.c:630/:647` have unrelated native data keys. They must not be equated with the reserved Painter store or globally banned by this task's checker.
